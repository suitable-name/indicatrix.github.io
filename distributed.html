Distributed rendering

Offloading sample tracing to a remote worker over mutual TLS.

1Preview-then-handoff

Spectral path tracing through a high-index gemstone with dozens of internal bounces is expensive, and streaming every interactive frame to a remote machine would add visible input latency. Indicatrix instead renders locally while the camera moves, and hands off to a remote indicatrix-worker once the camera settles: the client sends a compact SceneState (serialized with postcard) and the worker streams traced radiance back, which is folded into the client's own accumulation buffer.

2Sample-range additivity

Splitting a frame into screen-space tiles load-balances poorly for a gemstone render: background tiles finish almost instantly while tiles covering the stone itself carry the full bounce budget. Because each sample's RNG seed is a deterministic function of pixel index and sample number, sample contributions are additive and order-independent, so Indicatrix instead partitions work by sample-index range across the whole frame — one node traces samples [0, 64), another [64, 128), and so on — with no tile-seam stitching and linear load balancing across heterogeneous machines.

3Mutual TLS and token enrollment

The wire protocol lives in crates/indicatrix-net, typed message framing with no networking of its own. The worker's serve command carries the actual sockets and TLS.

  • TLS 1.3 only, via rustls with the ring crypto provider; TLS 1.2 is excluded from the feature set at compile time, not merely disabled at runtime (tls::server_config/tls::client_config).
  • Mutual authentication: both sides present a certificate signed by the same private CA (indicatrix-worker cert subcommands manage that CA).
  • A fingerprint allowlist decides which signed clients are actually trusted, separately from which CA signed them (--allowlist, off by default only with --trust-any-client-cert).
  • One-time token enrollment (crates/indicatrix-net/src/enroll): indicatrix-worker cert issue-token mints a short-lived token from the loopback side; cert claim redeems it, generating a keypair and requesting a signed certificate without a manual certificate exchange.
  • Plaintext serving (--insecure-no-tls) is available for local debugging and refused on any non-loopback bind address.

4The indicatrix-worker CLI

indicatrix-worker has three subcommands: render (one-shot scene-to-PNG, no networking), serve (the design-library protocol over TLS, plus render requests with the worker feature), and cert (manages the private CA). Flags below are copied from the CLI's own --help text in apps/indicatrix-worker/src/cli/mod.rs.

terminal — render
indicatrix-worker render \
  --scene scene.json \
  --out render.png \
  --width 3840 \
  --height 2160 \
  --samples 8192 \
  --threads 16

--only-gpu / --only-cpu force a backend; the default is a hybrid split across both when it measures as worthwhile.

terminal — serve
indicatrix-worker serve \
  --bind 0.0.0.0:9443 --allow-remote \
  --ca ca.pem --cert server.pem --key server.key

--bind defaults to loopback only (127.0.0.1:7878); --allow-remote is required for any other address. --db points at the design-library SQLite file (default facet_diagrams.sqlite). --max-connections defaults to 64.

5Pairing a worker with the desktop app

terminal — on the worker machine
# 1. create a CA
indicatrix-worker cert init

# 2. start serving
indicatrix-worker serve --bind 0.0.0.0:9443 --allow-remote \
  --ca ca.pem --cert server.pem --key server.key

# 3. mint a one-time enrollment token
indicatrix-worker cert issue-token

In indicatrix-cut, open the remote workers panel, enter the worker's address, and paste the enrollment token; the client redeems it (cert claim's wire equivalent), generates its own keypair, and completes the mutual-TLS handshake.
